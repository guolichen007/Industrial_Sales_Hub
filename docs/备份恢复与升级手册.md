# 备份、恢复与升级手册（RC2，2.1.0-rc2）

> 面向主机管理员。所有脚本需“以管理员身份运行”。普通员工不应执行主机运维脚本。
> 本手册描述的流程已在 Linux + PostgreSQL 16 上实测（自动化测试 + PowerShell 7 模拟验收，见第 8 节），
> **Windows 实机执行结果以 `RC2-Windows实机验收手册.md` 回传的证据为准**。

## 1. 运维互斥与维护状态

- 备份、正式恢复、升级、安装/修复、主体配置导入共用一把**全局运维锁** `data\ops.lock`（跨进程；进程崩溃或断电后由操作系统自动释放）。
  任何时刻只有一个运维任务运行；其他任务立即提示“另一个运维任务正在进行：<任务>（开始于…，进程…）”并以退出码 **75** 退出。
- 运行中的任务记录在 `data\ops.owner.json`，历史在 `data\ops.history.log`。
- 维护标记 `data\MAINTENANCE` 内容带任务 token，**只有放置它的任务能删除**。存在维护标记时，业务写请求返回 503（读照常）。
  升级/恢复失败且无法自动回退时，标记会**保留**以防在半完成数据上继续写入；此时 `06-检查系统.bat` 会列出未完成的任务与处理命令。
- 一致性边界：维护窗口内业务写入全部被拒；登录/登出/CSRF 不受限，`last_login` 与登录审计可能晚于备份快照——这属于已知豁免，不影响业务数据一致性。

## 2. 备份

`04-立即备份.bat`（计划任务调用 `backup.ps1 -Scheduled`）→ `manage.py ish_backup`：

1. 获取运维锁 → 放置带 token 的维护标记（新写请求 503）；
2. PostgreSQL advisory 排他锁等待已进入的写事务提交；
3. 锁内 `pg_dump`（自定义格式）+ 复制 `data\private`（报价 PDF、案例册、附件、照片、Logo）。**空系统也生成空的 `private\` 目录**（格式 2）；
4. 写 `manifest.json`（版本、迁移、表行数、文件清单与 SHA256）与 `SHA256SUMS`，在 `.tmp-*` 中自检后原子改名为 `ish-backup-<时间>[-标签]`；
5. 只删除自己的维护标记；原子写 `data\backup_status.json`；清理过期备份（永远保留本次）；
6. 若配置 `ISH_BACKUP_COPY_TO`：复制到副本目录的 `.tmp-*`，校验通过后改名；失败只告警，本机备份仍有效。

失败：不留半成品目录，上一个成功备份保留，状态文件记录错误。遇忙（75）：不写失败状态。
建议：RPO ≤ 24 小时（每日备份），RTO 以现场实测为准（第 8 节为沙箱参考值）。**禁止**直接复制运行中的 `data\pgdata` 作为备份。
备份目录含全部业务数据，只允许管理员与服务账户访问。

## 3. 恢复演练（不影响正式数据）

```bat
05-恢复备份.bat -BackupPath "D:\IndustrialSalesHub\backups\ish-backup-20261120-020000"
```
校验 SHA256 与清单 → 恢复到**新建临时数据库** + 安装目录下 `_ops-tmp\drill-*` → 完整性检查（表行数、报价快照/PDF 哈希、案例、附件、照片、Logo，
私有文件逐个与清单一致）→ 自动删除临时库与临时目录。RC1 生成的空备份（无 `private` 目录）同样可以演练与恢复。

## 4. 正式恢复（覆盖生产数据）

```bat
05-恢复备份.bat -BackupPath "<备份目录>" -Production
```
输入“确认恢复”后（`manage.py ish_restore` 状态机，日志 `data\ops\restore-<ID>.json/.log`）：

| 阶段 | 内容 | 失败时 |
|---|---|---|
| VERIFY | 校验备份（SHA256/清单/format）；**拒绝来自更新程序版本的备份**；检查磁盘空间（staging 库 + staging 文件 + 保留旧数据）；正式库无其他连接 | 不做任何改动，状态记为 `FAILED_PRECHECK`（见下） |
| LOCKED | 运维锁 + 维护标记；确认应用已停止、正式库无连接 | 不做任何改动 |
| SAFETY_BACKUP | 先对**当前状态**做一次一致性备份（`*-before-restore-<ID>`） | 不做任何改动 |
| STAGE_DB | 新建 staging 库并 `pg_restore --single-transaction`；旧 schema 备份在 staging 上迁移到当前版本 | 删除 staging，正式数据未动 |
| STAGE_FILES | 复制到 `data\private.restore-<ID>` 并逐个核对 SHA256 | 同上 |
| STAGE_VERIFY | 对 staging 库 + staging 文件运行完整性检查 | 同上 |
| SWITCH | **只用改名**：正式库→`<库>_old_<ID>`、staging→正式库；`private`→`private.old-<ID>`、staging 文件→`private` | 按日志逆序撤销改名 |
| POST_VERIFY | 对切换后的正式库与文件再次完整性检查 | 撤销切换 |
| DONE | 解除自己的维护标记 | — |

脚本随后设置目录权限并启动应用；若权限设置或启动失败，会自动执行 `--rollback` 撤销本次切换（退出码 41）。
恢复成功后旧库与旧文件保留：确认业务无误后 `05-恢复备份.bat -Cleanup <ID>` 删除；发现问题可 `05-恢复备份.bat -Rollback <ID>` 回到恢复前。
**禁止**在恢复过程中手工改动 `data\` 目录；**禁止手工删除 `data\MAINTENANCE` 维护标记**（维护标记只能由同一次恢复进程自行解除）。

### 恢复状态、退出码与处置（`data\ops\restore-<ID>.json` 的 `state`）

| state | 含义 | 正式数据 | 应用服务 | 包装脚本退出码与处置 |
|---|---|---|---|---|
| `FAILED_PRECHECK` | **前置拒绝**：备份校验/版本兼容/磁盘/连接/维护标记等预检查未通过，未执行本次切换 | 本次未改动 | 满足下述条件才恢复启动 | 服务确认健康为 **40**，仍受维护或启动、探活未通过为 **42** |
| `RUNNING` | 恢复正在进行，或进程被强制结束后仍有不确定步骤 | 不确定 | **保持停止**（保护） | 退出码 **42**；不要改动 `data\`，运行 `05-恢复备份.bat -Rollback <ID>` 或按 §6 处理 |
| `ROLLED_BACK` | 切换前/切换后失败，**已自动完整回退**到恢复前 | 回到恢复前 | 满足下述条件才恢复启动 | 服务确认健康为 **40**，仍受维护或启动、探活未通过为 **42** |
| `ROLLBACK_FAILED` | 自动回退本身失败（极少见，如改名被占用/杀毒锁文件） | **不确定，需人工** | **保持停止**（保护） | 退出码 **42**；保留现场，把 `data\ops\`、`logs\` 交给实施人员 |
| `DONE` | 恢复完成 | 备份内容 | 已启动并探活 | 退出码 **0**；确认后可 `-Cleanup` |

新恢复获取运维锁后，先检查 `data\MAINTENANCE`。存在遗留标记时返回 **42**，保留标记字节与应用原有状态。运行 `06-检查系统`，依据原任务日志按第 6 节处理。

本次恢复失败时，`FAILED_PRECHECK`、`ROLLED_BACK` 或尚未生成本次日志的情况可以在无维护标记时尝试启动应用。只有服务处于 `Running` 且 `/healthz` 返回 HTTP 200、`status=ok`、`maintenance=false` 才记录应用已恢复并返回 **40**。启动或探活失败返回 **42**，脚本尝试停止应用并记录失败原因。`RUNNING` 和 `ROLLBACK_FAILED` 保持停止与保护状态。维护标记由持有它的运维任务管理。

## 5. 升级

1. 把新版本 ZIP 核对 SHA256 后解压到**另一个目录**（例如 `D:\ISH-2.1.1`，不能在安装目录之内）；
2. 在**新版本目录**以管理员身份运行：`07-升级程序.bat -InstallDir "D:\IndustrialSalesHub"`；
3. 升级器（日志 `data\ops\upgrade-<ID>.json`）：

| 阶段 | 内容 |
|---|---|
| PRECHECK | 新包 SHA256 全量校验（拒绝路径穿越与含 data/config 的包）；禁止降级；同版本需 `-Repair`；PostgreSQL 大版本必须一致（跨大版本需专门的 pg_upgrade 流程，升级器拒绝）；磁盘空间；路径安全 |
| LOCK | 运维锁 + 维护标记；停止应用 |
| BACKUP | **用旧程序、旧运行时**生成 `*-pre-upgrade-<ID>` 一致性备份，并用旧程序做恢复演练 |
| SNAPSHOT | `CREATE DATABASE <库>_preupg_<ID> TEMPLATE <库>`：整库快照，回滚时直接改名切回 |
| STAGE | 新发行文件复制到 `_upgrade\<ID>\new` 并再次全量校验 |
| SWITCH | 停数据库 → 旧发行文件**整套**（app、runtime、scripts、*.bat、VERSION、SHA256SUMS、licenses、config-templates、说明文档）移到 `_upgrade\<ID>\old` → 新文件移入 → 安装目录与新清单逐文件一致 |
| MIGRATE | 启动数据库 → 新程序 `ish_upgrade --pre-backup <该 ID 的备份>`（不再自行备份）：迁移 + 完整性校验（含历史报价 PDF 原字节哈希） |
| VERIFY | 启动应用，`/healthz` 版本必须等于新版本 |

`data`、`config`、`backups`、`logs`、`services` 永不移动。任何阶段失败：**自动按日志逆序回滚**（发行文件移回、数据库从快照改名切回、迁移过的库保留为 `<库>_failed_<ID>` 供分析），
回滚后再次校验旧清单、运行旧程序完整性检查、启动并核对旧版本号（退出码 56）。回滚也失败时系统保持维护只读（退出码 57），按屏幕提示联系实施人员。

- 断电/进程被杀：重新开机后在**新版本目录**运行 `07-升级程序.bat -InstallDir <安装目录> -Rollback <ID>`（或在安装目录运行，升级器会先把自己复制到临时目录再执行）。
- 升级成功后发现问题：`<安装目录>\07-升级程序.bat -Rollback <ID>`（会提示：升级后录入的数据将随快照切回而丢失，它们仍在 `_failed_` 库中）。
- 确认新版本运行正常（建议一周）：`<安装目录>\07-升级程序.bat -Cleanup <ID>` 删除旧版本文件与数据库快照。
- 查看历史：`07-升级程序.bat -Status`。

## 6. 维护状态未解除时怎么办

1. 运行 `06-检查系统.bat`：若显示“当前运维任务…”，等待其结束；
2. 若显示“没有正在运行的运维任务”并列出 `upgrade-*`/`restore-*` 未完成：分别执行 `07-升级程序.bat -Rollback <ID>` 或 `05-恢复备份.bat -Rollback <ID>`；
3. 仍无法解除：保留现场（不要删除 `data\MAINTENANCE`、不要改动 `data\`），把 `data\ops\`、`logs\` 交给实施人员。

## 7. 计划任务与异盘副本

`08-配置每日备份.bat [-At 02:00]`：以 SYSTEM 运行、错过时补做、`MultipleInstances=IgnoreNew`；其他运维任务进行中时最多等待 30 分钟，仍忙则跳过（75）。
异盘副本 `ISH_BACKUP_COPY_TO` 建议设置为另一块物理硬盘；网络共享需对“主机计算机账户”授权（SYSTEM 以计算机账户访问网络），现场单独验证。
