# 备份、恢复与升级手册（V2.1-LAN）

## 1. 备份如何保证一致

`04-立即备份.bat` 调用 `manage.py ish_backup`：

1. 放置 `data\MAINTENANCE` 维护标志：此后新的**写请求**返回“系统正在备份或维护”（只读访问不受影响）；
2. 获取 PostgreSQL advisory **排他锁**：每个写请求在事务中持有同一把锁的共享锁，因此排他锁会**等待所有已进入的写操作提交**；
3. 在锁内同时完成 `pg_dump`（自定义格式）与 `data\private`（报价 PDF、案例册、附件）复制；
4. 写 `manifest.json`（版本、迁移、各表行数、文件清单与哈希）与 `SHA256SUMS`，先写到 `.tmp-*`，自检通过后原子改名为 `ish-backup-<时间>`；
5. 释放锁、删除维护标志（异常时 `finally` 保证恢复服务）；更新 `data\backup_status.json`。

失败时：不产生半成品目录，**上一个成功备份保留**，状态文件记录错误，`06-检查系统` 与管理员首页会显示。
默认保留 30 天（`ISH_BACKUP_KEEP_DAYS`），永远保留最近一个成功备份。**禁止**直接复制或压缩运行中的 `data\pgdata` 作为备份。

建议：RPO ≤ 24 小时（每日备份），RTO ≤ 2 小时（以实测为准）。至少保留一份**异盘或异机**副本（`ISH_BACKUP_COPY_TO`）。
备份目录含全部业务数据与 PDF，只允许管理员与服务账户访问；不要放到公共共享盘。

## 2. 恢复演练（不影响正式数据）

```bat
05-恢复备份.bat -BackupPath "D:\IndustrialSalesHub\backups\ish-backup-20261119-020000"
```

流程：校验 SHA256 与清单 → 恢复到**新建临时数据库** + **新临时目录** → 用临时库运行完整性检查（用户/角色、各表行数与清单一致、
报价快照与 PDF 哈希、案例册、附件）→ 自动删除临时库与临时目录。以下情况会被拒绝并报错：文件被篡改、缺文件、多出未登记文件、
清单损坏、`db.dump` 截断、缺少校验文件、恢复目标是正式库或正式数据目录、临时库已存在。

## 3. 正式恢复（覆盖生产数据）

```bat
05-恢复备份.bat -BackupPath "<备份目录>" -Production
```

需要管理员，并输入“确认恢复”。脚本会：先校验备份 → **先对当前状态再做一次备份**（`*-before-restore`）→ 停止应用 →
`pg_restore --single-transaction --clean`（失败则数据库保持原样并重新启动应用）→ 用备份替换 `data\private`（旧目录改名保留）→
完整性校验 → 启动应用。

## 4. 升级

1. 把新版本 ZIP 解压到**另一个目录**（例如 `D:\ISH-2.1.1`），核对 SHA256；
2. 以管理员身份运行：`07-升级程序.bat -NewPackageDir "D:\ISH-2.1.1"`；
3. 脚本：停止应用 → 旧 `app` 改名保留 → 复制新程序 → `ish_upgrade`（先做 `*-pre-upgrade` 一致性备份 → 维护模式下迁移 → 完整性校验）→ 启动 → 探活。

### 迁移失败如何回滚

迁移失败时系统**保持只读维护模式**（禁止在部分迁移的数据库上继续写入），并在 `data\upgrade_status.json` 记录原因。按屏幕提示：

1. 删除新 `app`，把 `app.old-<版本>-<时间>` 改回 `app`，把 `runtime.old-*` 改回 `runtime`；
2. `05-恢复备份.bat -BackupPath "<backups 中最新的 *-pre-upgrade>" -Production`；
3. 删除 `data\MAINTENANCE`，运行 `02-启动系统.bat`。

**不允许**用覆盖旧数据库文件的方式回退。
